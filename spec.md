# Wardrobe App — Technical Spec

Oct 28, 2026 · @Kai Zhang

## 1. Overview

A single-owner wardrobe site on Cloudflare Workers: the owner logs one outfit per day from an admin view, and the public browses items, outfits, stats, a daily "should wear" leaderboard, and visitor-submitted outfit suggestions.

**Guiding principles (apply everywhere):**

- **One writer, many readers, tiny data.** The owner is the only writer of wardrobe data. The dataset stays in the low megabytes. Do not add caching layers, queues, or services the requirements do not call for.
- **The outfit-day is the core unit.** At most one outfit per calendar date. Item stats (wear count, last worn, enjoyment) are derived from outfit membership, never stored as counters.
- **Compute on read, except rankings.** All stats are SQL queries at request time. The only snapshot is the daily ranking, because it depends on the day's forecast and must be identical for every visitor all day.
- **Dates and times.** Calendar dates are `TEXT` in `YYYY-MM-DD`, interpreted in `SITE_TZ` (America/Toronto). Timestamps are `INTEGER` Unix milliseconds, UTC. Never derive a calendar date from `new Date()` without converting to `SITE_TZ`.
- **Publishing delay.** Public views only see outfits on or before the publish cutoff (section 10). This includes derived stats and rankings, so nothing public reveals what the owner is wearing today.
- **Server validates everything.** Every write is validated with Zod on the server. Client validation is a convenience only.
- **Public text is plain text.** Visitor names and messages are rendered as escaped text. No HTML, no Markdown, never `dangerouslySetInnerHTML`.
- **No prices anywhere.** No price column, no cost-per-wear.

**Out of scope for the MVP:** NFC logging, a native mobile app, multi-user accounts, prices, an algorithmic outfit generator, laundry tracking, analytics dashboards.

## 3. Database schema (D1 / SQLite)

This DDL is the source of truth; the Drizzle schema must reproduce it exactly, including CHECK constraints and partial indexes. D1 enforces foreign keys by default.

### Wardrobe

```sql
CREATE TABLE items (
  id            TEXT PRIMARY KEY,
  name          TEXT NOT NULL CHECK (length(name) BETWEEN 1 AND 80),
  slot          TEXT NOT NULL CHECK (slot IN ('top','bottom','outerwear','shoes','accessory')),
  color         TEXT CHECK (color IS NULL OR length(color) <= 40),
  brand         TEXT CHECK (brand IS NULL OR length(brand) <= 60),
  acquired_on   TEXT CHECK (acquired_on IS NULL OR acquired_on GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'),
  anecdote      TEXT CHECK (anecdote IS NULL OR length(anecdote) <= 4000),
  -- photo: R2 base key + format + full-size dimensions (section 9)
  photo_key     TEXT,
  photo_ext     TEXT CHECK (photo_ext IS NULL OR photo_ext IN ('webp','jpg')),
  photo_w       INTEGER,
  photo_h       INTEGER,
  -- optional manual temperature prior for season fit, apparent degC (section 5)
  temp_min_c    REAL,
  temp_max_c    REAL,
  archived_at   INTEGER,
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  CHECK ((photo_key IS NULL) = (photo_ext IS NULL)),
  CHECK (temp_min_c IS NULL OR temp_max_c IS NULL OR temp_min_c < temp_max_c)
);
CREATE INDEX items_active_slot ON items(slot) WHERE archived_at IS NULL;

CREATE TABLE outfits (
  date                  TEXT PRIMARY KEY
                        CHECK (date GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'),
  rating                INTEGER CHECK (rating IS NULL OR rating BETWEEN 1 AND 10),
  note                  TEXT CHECK (note IS NULL OR length(note) <= 2000),
  fit_pic_key           TEXT,
  fit_pic_ext           TEXT CHECK (fit_pic_ext IS NULL OR fit_pic_ext IN ('webp','jpg')),
  fit_pic_w             INTEGER,
  fit_pic_h             INTEGER,
  source_suggestion_id  TEXT REFERENCES suggestions(id) ON DELETE SET NULL,
  created_at            INTEGER NOT NULL,
  updated_at            INTEGER NOT NULL,
  CHECK ((fit_pic_key IS NULL) = (fit_pic_ext IS NULL))
);
CREATE INDEX outfits_source_suggestion ON outfits(source_suggestion_id)
  WHERE source_suggestion_id IS NOT NULL;

CREATE TABLE outfit_items (
  date     TEXT NOT NULL REFERENCES outfits(date) ON DELETE CASCADE,
  item_id  TEXT NOT NULL REFERENCES items(id) ON DELETE RESTRICT,
  PRIMARY KEY (date, item_id)
) WITHOUT ROWID;
CREATE INDEX outfit_items_by_item ON outfit_items(item_id, date);
```

### Design notes

- **`outfits.date` is the primary key.** This enforces one outfit per day, makes the date the URL, and gives weather a direct join. Layering is allowed: an outfit may contain several items in the same slot.
- **The suggestion link lives on `outfits`.** One suggestion can be worn on several days, but each outfit comes from at most one suggestion, so the foreign key belongs on `outfits.source_suggestion_id`.
- **Items are never hard-deleted once referenced.** `ON DELETE RESTRICT` from `outfit_items` and `suggestion_items` forces archiving via `archived_at`. Unreferenced items may be deleted.
- **No stored counters.** Wear count, last worn, and average rating are always queried (section 4).
- **Rankings are per-date snapshots** with their component scores, so the leaderboard can explain each rank and show history.
- **Rows in `ranking_runs` and `rankings` for a date are replaced together** in one `db.batch`, which keeps the cron idempotent.
- **Table creation order** in the first migration: `items`, `suggestions`, `suggestion_items`, `outfits`, `outfit_items`, `weather`, `ranking_runs`, `rankings`, `blocked_ips`, `admin_credentials`, `sessions` (`outfits` references `suggestions`).

## 4. Derived queries and stat definitions

Every public query takes a `:cutoff` parameter (the publish cutoff, section 10) and ignores outfits after it; admin queries pass today's date instead.

**Effective temperature** for a day is `(apparent_max_c + apparent_min_c) / 2`. Clothing choice tracks feels-like temperature, so apparent temperature is used everywhere instead of air temperature.

### Per-item stats

```sql
SELECT
  i.id,
  COUNT(oi.date)                                         AS wear_count,
  MAX(oi.date)                                           AS last_worn,
  MIN(oi.date)                                           AS first_worn,
  AVG(o.rating)                                          AS avg_rating,
  COUNT(o.rating)                                        AS rated_count,
  AVG((w.apparent_max_c + w.apparent_min_c) / 2.0)       AS avg_worn_temp,
  COUNT(w.date)                                          AS temp_samples
FROM items i
LEFT JOIN outfit_items oi ON oi.item_id = i.id AND oi.date <= :cutoff
LEFT JOIN outfits o       ON o.date = oi.date
LEFT JOIN weather w       ON w.date = oi.date AND w.kind = 'actual'
WHERE i.archived_at IS NULL            -- omit on item detail pages for archived items
GROUP BY i.id;
```

`avg_rating` here is the raw mean, shown on item pages. The leaderboard uses a shrunk version (section 5).

### Item detail extras

**Wear dates for the heatmap:** `SELECT date FROM outfit_items WHERE item_id = :id AND date <= :cutoff ORDER BY date`. Render a 53-week grid ending at the cutoff, as server-side SVG.

**Most often worn with (top 5):**

```sql
SELECT b.item_id AS other_id, COUNT(*) AS together, AVG(o.rating) AS avg_rating
FROM outfit_items a
JOIN outfit_items b ON b.date = a.date AND b.item_id <> a.item_id
JOIN outfits o      ON o.date = a.date
WHERE a.item_id = :id AND a.date <= :cutoff
GROUP BY b.item_id
ORDER BY together DESC, avg_rating DESC
LIMIT 5;
```

### Wardrobe-wide stats (`/stats`)

| Stat | Definition |
| --- | --- |
| Total outfits logged | `COUNT(*)` of outfits on or before the cutoff |
| Average outfit rating | Mean of non-null ratings |
| Logging streak | Longest run of consecutive dates with an outfit; current run ending at the cutoff |
| Concentration | Sort active items by wear count, descending. Find the smallest set whose wears sum to at least 50% of all wears. Display: "X% of items account for half of all wears." Computed in application code from the per-item query. |
| Dormant items | Active items never worn, or with `last_worn` more than 90 days before the cutoff, oldest first |
| Wears by slot | Wear count grouped by `items.slot` |
| Rating vs temperature | Average rating grouped into 5 °C buckets of effective temperature |
| Visitor suggestions vs own picks | Query below |

```sql
SELECT (source_suggestion_id IS NOT NULL) AS from_visitor,
       COUNT(*)    AS outfits,
       AVG(rating) AS avg_rating
FROM outfits
WHERE date <= :cutoff AND rating IS NOT NULL
GROUP BY from_visitor;
```

### Random outfit

`SELECT date FROM outfits WHERE date <= :cutoff ORDER BY random() LIMIT 1`, then a 302 redirect to `/outfits/:date` with `Cache-Control: no-store`. A full scan is fine at this data size. With no outfits, redirect to `/outfits`.

## 5. Leaderboard algorithm

Each day every active item gets a score in \[0, 1\]; season fit multiplies the rest so out-of-season items sink regardless of their other terms.

```latex
\text{score}_i = F_i \cdot \left( w_r R_i + w_e E_i + w_u U_i \right), \quad w_r + w_e + w_u = 1
```

Implement the scorer as a **pure function** in `app/lib/ranking.ts`: inputs are plain arrays (items, published wears with ratings and effective temperatures, today's effective temperature T, params); output is the scored, ranked list. No database access inside it, so it is unit-testable.

**Inputs.** Only outfits on or before the publish cutoff count. The candidate set is all items with `archived_at IS NULL`. T is today's effective temperature from the `weather` row for today.

### Season fit F (0–1)

A Gaussian around the temperature the item is usually worn at, blending a prior with observed history:

```latex
F_i = \exp\left( -\frac{(T - \mu_i)^2}{2 \sigma_i^2} \right)
```

```latex
\mu_i = \frac{k \mu_0 + n \bar{t}}{k + n}, \qquad \sigma_i = \max\left( \sigma_{\min}, \frac{k \sigma_0 + n s}{k + n} \right)
```

Here n is the number of the item's wears with an `actual` weather row, t̄ is their mean effective temperature, and s is their sample standard deviation (use σ0 when n < 2). The prior (μ0, σ0) comes from the item's manual `temp_min_c`/`temp_max_c` when both are set, as μ0 = midpoint and σ0 = (max − min) / 4. Otherwise it comes from the slot default below.

### Recency R (0–1)

```latex
R_i = 1 - e^{-d_i / \tau}
```

d is days from the item's last published wear to today. Never-worn items get R = 1.

### Enjoyment E (0–1)

A Bayesian average of the ratings of outfits containing the item, shrunk toward the global mean m so one great day cannot dominate:

```latex
\tilde{r}_i = \frac{C m + \sum r}{C + n_r}, \qquad E_i = \frac{\tilde{r}_i - 1}{9}
```

n\_r is the number of rated outfits containing the item. m is the mean of all published ratings, or 6 if there are none.

### Underuse U (0–1)

Wear rate = wears / max(days owned, 30), where days owned runs from the earliest of `acquired_on`, first wear, or `created_at` (as a local date) to the cutoff. U = 1 − percentile rank of the item's wear rate among candidates (ties take the average percentile). Percentiles make the term robust to a few heavily worn items.

### Parameters (stored in `ranking_runs.params_json`)

| Parameter | Default | Meaning |
| --- | --- | --- |
| w\_r | 0.4 | Recency weight |
| w\_e | 0.4 | Enjoyment weight |
| w\_u | 0.2 | Underuse weight |
| τ | 21 days | Recency time constant |
| C | 3 | Enjoyment shrinkage strength (pseudo-ratings) |
| k | 3 | Season prior strength (pseudo-wears) |
| σ\_min | 4 °C | Floor on season width |
| Prior, `outerwear` | μ0 = 2 °C, σ0 = 7 °C | Cold-weather default |
| Prior, other slots | μ0 = 12 °C, σ0 = 14 °C | Broad, near year-round default |

Keep parameters in one exported constant object with a `version` field, and write the whole object to `params_json` on every run.

### Ranking and display

- Rank by score descending; tie-break by older `last_worn` first (never worn first), then by `id`.
- Store every candidate's rank, score, and four components in `rankings`.
- `/leaderboard` shows the top 20 for today with photos, score, and a short explanation built from the components, such as "Hasn't been worn in 6 weeks · fits today's 4 °C · you rate it 8.1".
- Each entry shows movement versus yesterday's rank when yesterday's run exists.
- The home page shows the top 5.

## 6. Daily cron: weather and rankings

One idempotent job, `runDaily(env, { force })`, runs from the `scheduled` handler and from the admin re-run button; running it twice in a day is always safe.

**Schedule.** `0 9 * * *` UTC is the primary run (04:00 EST / 05:00 EDT). `0 15 * * *` is a safety run that exits early if `ranking_runs` already has an `ok` row for today. Cron times are UTC, but all date logic uses `SITE_TZ`.

**Steps:**

1. Compute `today` in `SITE_TZ`, and `cutoff` (section 10).
2. **Recent weather.** One request to the Open-Meteo forecast API at `SITE_LAT`/`SITE_LON` with `daily=temperature_2m_max,temperature_2m_min,apparent_temperature_max,apparent_temperature_min,precipitation_sum,weather_code`, `timezone=America/Toronto`, `past_days=7`, `forecast_days=1`.
3. **Upsert weather.** Dates before today are written as `kind = 'actual'`; today is written as `kind = 'forecast'`. Rule: a `forecast` row may be replaced by anything, but an `actual` row is never replaced by a `forecast`. Use `INSERT ... ON CONFLICT(date) DO UPDATE ... WHERE weather.kind = 'forecast' OR excluded.kind = 'actual'`.
4. **Backfill.** Find outfit dates with no `actual` weather row. Dates within the last 90 days are covered by re-requesting the forecast API with a larger `past_days` (max 92). Older dates use the Open-Meteo archive API with `start_date`/`end_date` spanning the missing range. Cap backfill at 365 days per run; later runs continue where it left off.
5. **Rankings.** Load candidates and published wears, take T from today's weather row, and run the pure scorer (section 5).
6. **Write atomically.** In one `db.batch`: delete `ranking_runs` for today (cascades to `rankings`), insert the new `ranking_runs` row, then insert all `rankings` rows.
7. **Housekeeping.** Delete expired `sessions`. Delete `rejected` suggestions older than 90 days.

**Failure handling:**

- Fetch with a 10-second timeout and up to 2 retries with backoff.
- If today's forecast cannot be fetched, use the most recent weather row's effective temperature and write the run with `status = 'degraded'`. If there is no weather at all, set F = 1 for every item and mark `degraded`.
- An exception in steps 2–4 must not prevent step 5–6. Log with `console.error` and a structured object (`{ job: 'daily', step, error }`) so it appears in Workers logs.
- `/admin` shows the latest run's status and time, with a "Re-run now" button that calls `runDaily(env, { force: true })`.

### Write contracts (Zod)

```ts
const isoDate = z.string().regex(/^\d{4}-\d{2}-\d{2}$/);

export const UploadRef = z.object({
  key: z.string().regex(/^(items|fits)\/[\w-]+\/[0-9a-f-]{36}$/),
  ext: z.enum(['webp', 'jpg']),
  w: z.number().int().positive(),
  h: z.number().int().positive(),
});

export const ItemInput = z.object({
  name: z.string().trim().min(1).max(80),
  slot: z.enum(['top', 'bottom', 'outerwear', 'shoes', 'accessory']),
  color: z.string().trim().max(40).optional(),
  brand: z.string().trim().max(60).optional(),
  acquiredOn: isoDate.optional(),
  anecdote: z.string().trim().max(4000).optional(),
  tempMinC: z.coerce.number().min(-40).max(45).optional(),
  tempMaxC: z.coerce.number().min(-40).max(45).optional(),
  photo: UploadRef.optional(),
}).refine(v => v.tempMinC == null || v.tempMaxC == null || v.tempMinC < v.tempMaxC);

export const OutfitInput = z.object({
  date: isoDate,                                  // must be <= today in SITE_TZ
  itemIds: z.array(z.string().uuid()).min(1).max(15),
  rating: z.coerce.number().int().min(1).max(10).optional(),
  note: z.string().trim().max(2000).optional(),
  fitPic: UploadRef.optional(),
  sourceSuggestionId: z.string().uuid().optional(),
});
```

**Outfit save semantics.** Reject future dates and duplicate item ids. Every item id must exist; archived items are allowed only if they were already in this outfit. `sourceSuggestionId`, when present, must reference an `approved` suggestion. Write in one `db.batch`: upsert the `outfits` row, delete its `outfit_items`, insert the new set.

**Caching.** Public GET responses are cached in `caches.default` for 60 seconds, keyed by URL, with `Cache-Control: public, max-age=0, s-maxage=60`. Never cache admin routes, `/outfits/random`, or POST responses. No purge logic in the MVP; owner edits appear publicly within a minute.

## 8. Visitor suggestions

Visitors build an outfit from the owner's active items and may add a name and message; nothing a visitor writes is public until the owner approves it.

### Slot rules for suggestions

Keep these in one exported constant (`SUGGESTION_SLOT_RULES`). Owner-logged outfits are not bound by them.

| Slot | Min | Max |
| --- | --- | --- |
| top | 1 | 2 |
| bottom | 1 | 1 |
| shoes | 1 | 1 |
| outerwear | 0 | 1 |
| accessory | 0 | 2 |

### Submission contract

```ts
export const SuggestionInput = z.object({
  itemIds: z.array(z.string().uuid()).min(3).max(7),
  name: z.string().optional(),       // normalized, then 1..40 chars or dropped
  message: z.string().optional(),    // normalized, then 1..280 chars or dropped

});
```

### `POST /suggest` pipeline (in order)

1. **Hash the IP.** `ip_hash` = hex SHA-256 of `IP_HASH_SALT + CF-Connecting-IP`. The raw IP is never stored or logged.
2. **Rate limit.** `env.SUGGEST_LIMITER.limit({ key: ip_hash })`. On failure return 429 with a friendly message.
3. **Verify Turnstile.** POST to Turnstile's `siteverify` with the secret, token, and `remoteip`. On failure return 400. Tokens are single-use, which also blocks double-submits.
4. **Parse and normalize.** Run Zod. For `name` and `message`: Unicode NFC, strip control and zero-width characters, collapse whitespace runs, trim. Empty after normalization becomes `NULL`.
5. **Reject links.** If `name` or `message` matches `/(https?:\/\/|www\.|\b[a-z0-9-]+\.(com|net|org|io|co|ca|xyz|ru|me|app|dev|link)\b)/i`, return 400 explaining links are not allowed.
6. **Validate items.** All ids unique, all exist, all `archived_at IS NULL`, and per-slot counts satisfy `SUGGESTION_SLOT_RULES`.
7. **Daily cap.** If this `ip_hash` has 10 or more suggestions in the last 24 hours, return 429.
8. **Queue cap.** If 200 or more suggestions are `pending`, return 503 with "Suggestions are paused while I catch up."
9. **Compute `combo_key`.** Sort item ids ascending, join with `,`, hex SHA-256.
10. **Insert.** One `db.batch`: insert `suggestions` (status `pending`) and its `suggestion_items`. If `ip_hash` is in `blocked_ips`, insert with status `rejected` and `reviewed_at` set instead (shadow rejection; the visitor sees the normal success page).
11. **Respond.** Redirect to `/suggest?sent=1`, which shows "Thanks, I'll review it soon."

Error responses never reveal which check failed beyond what the visitor can fix (a link, a slot rule, slow down).

### Moderation

- `/admin/suggestions` lists pending suggestions oldest first, showing item photos, name, message, and how many approved suggestions share the same `combo_key`.
- `approve` sets status `approved`, `reviewed_at`. `approve_hide_text` does the same and sets `text_hidden = 1`. `reject` sets status `rejected`. `block_ip` rejects and inserts the `ip_hash` into `blocked_ips`.
- Each approved suggestion has a "Wear this" link to `/admin/outfits/:today?from_suggestion=:id`, which pre-selects its items and sets `sourceSuggestionId`.

### Public display (`/suggestions`)

- Only `status = 'approved'` rows appear. When `text_hidden = 1` or `name` is null, show "Anonymous" and no message.
- `sort=recent`: newest approved first, 20 per page. `sort=popular`: group by `combo_key`, ordered by count, showing the count ("Suggested by 6 people") and the most recent visible message.
- A suggestion shows a "Worn" badge, linking to the outfit, only if an outfit with that `source_suggestion_id` exists on or before the publish cutoff.
- All visitor text is rendered as plain text through normal JSX escaping.

## 9. Images

Images are resized and re-encoded in the admin's browser, stored in R2 under unguessable immutable keys, and served through the Worker; there is no server-side image processing.

### Client-side processing (admin only)

1. Decode with `createImageBitmap(file, { imageOrientation: 'from-image' })` so phone photos are upright.
2. Draw onto a canvas at two sizes: **480 px** and **1600 px** on the long edge (never upscale).
3. Encode with `canvas.toBlob(cb, 'image/webp', 0.82)`. If the resulting blob's type is not `image/webp` (some Safari versions), re-encode as `image/jpeg` at 0.85 and use `jpg` for both variants.
4. Re-encoding through a canvas drops all EXIF metadata, including GPS location. Do not use any library that copies metadata across.
5. Upload both variants in one `multipart/form-data` POST to `/admin/uploads` with fields `kind` (`item` or `fit`), `owner` (item id or outfit date), `w`, `h` (full-size dimensions), `small`, `large`.

### Upload endpoint

- Require an admin session and a matching `Origin`.
- Check each file's magic bytes (`RIFF....WEBP` or `FF D8 FF`), not just its declared type. Each file must be at most 1.5 MB.
- Generate `key = {items|fits}/{owner}/{uuid}` and write `{key}-480.{ext}` and `{key}-1600.{ext}` to R2 with the correct `contentType`.
- Return the `UploadRef` (`key`, `ext`, `w`, `h`). The item or outfit form then saves that reference.
- When an item or outfit's photo is replaced or removed, delete the old R2 objects after the database write succeeds. A weekly sweep is unnecessary for the MVP; orphaned uploads from abandoned forms are acceptable.

### Serving: `GET /media/*`

- Only paths matching `^(items|fits)/[\w-]+/[0-9a-f-]{36}-(480|1600)\.(webp|jpg)$` are served; anything else is 404.
- **Fit pics respect the publishing delay.** For `fits/{date}/...`, return 404 unless the date is on or before the publish cutoff or the request carries a valid admin session. Fit-pic responses for not-yet-published dates must use `Cache-Control: private, no-store`.
- Published responses use `Cache-Control: public, max-age=31536000, immutable`, since a key's content never changes. Serve through `caches.default` and pass R2's `etag`.

### Rendering

Use `<img srcset>` with both variants (`480w`, `1600w`), explicit `width`/`height` from the stored dimensions to prevent layout shift, `loading="lazy"` below the fold, and `decoding="async"`. Items without a photo show a neutral placeholder with the item name.

## 10. Auth, publishing, build order

### Admin auth (passkeys)

- **Registration** (`/admin/setup`): allowed with `?token=` equal to `ADMIN_SETUP_TOKEN` when `admin_credentials` is empty, or with a valid session afterwards (to add a second device). Use `@simplewebauthn/server` with `rpID = RP_ID`, `expectedOrigin = ORIGIN`, `userVerification: 'required'`.
- **Challenges** are stored in a signed, HttpOnly, 5-minute cookie (HMAC-SHA-256 keyed by `IP_HASH_SALT`), not in the database.
- **Login** verifies the assertion, updates `counter` and `last_used_at`, then creates a session.
- **Sessions**: 32 random bytes, base64url, in cookie `__Host-session` with `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=2592000` (30 days). Store only the SHA-256 hash in `sessions`.
- **CSRF**: `SameSite=Lax` plus the `Origin` check on every admin POST.

### Publishing delay

```ts
// today = current calendar date in SITE_TZ
cutoff = addDays(today, -PUBLISH_DELAY_DAYS);   // public sees outfits with date <= cutoff
```

With the default of 1, an outfit becomes public the day after it is worn. The cutoff applies to: outfit list and pages, random outfit, every stat, ranking inputs, "Worn" badges on suggestions, and fit-pic media. Admin views use `today`. Put this in one function, `publishCutoff(env, now)`, used everywhere, with unit tests around midnight and DST changes.
